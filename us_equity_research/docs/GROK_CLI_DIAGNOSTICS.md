# Grok CLI 远程搜索诊断

检查日期：2026-09-13。目标：用户指定的 box，Grok Build CLI 1.0.4。

## 已验证结果

| 测试 | 完成时间 | 结果 |
|---|---:|---|
| 禁用工具的模型回复 | 12.5 秒 | 正常退出并返回测试文本 |
| 单次 Microsoft IR 网页搜索 | 14.3 秒 | 工具实际执行，返回官方来源，正常退出 |
| MSFT 单主题、最多两次搜索 | 32.4 秒 | 实际执行两次搜索并返回结果 |
| 原四主题 FinTwit 搜索 | 193.9 秒 | 实际执行16次搜索，正常退出，返回6条主条目及额外检索备注 |

四主题复现中，约71秒完成最后一批搜索；142、162、182秒仍有答案文本增长；192.8秒收到 end_turn，193.9秒进程退出。整个复现没有观察到权限等待或搜索工具失败。返回链接、日期及观点尚未由本系统独立核验，不能直接作为正式证据。

## 超时归因

上一次160秒来自调用端 Python subprocess 的总时限，不是 Grok 服务端返回的超时错误。此前调用一次性捕获最终 stdout，超时分支又没有展示部分结果，因而看起来像没有进展。原次没有完整进度记录，不能断言其每个内部步骤；本次同提示复现明确显示，多主题搜索和长答案生成需要超过160秒。

另有独立的网络问题：SSH会话没有继承系统代理。沿用远程机器现有的 localhost:7897 代理，仅为该次子进程设置 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 后请求可成功。没有更改全局代理、账户或凭据。

## 调用策略

- 简单搜索保留60–90秒总预算；多主题任务采用300秒总预算。本次300秒已实际验证足够，但不保证每次都足够。
- 使用 streaming-json；分别观察工具开始/结束、输出增长、最终 end_turn 与进程退出。不要把本地超时、工具错误、结果为空和正常结束混为一谈。
- 白名单化输出：只保留事件时间、工具状态、计数与必要答案；不持久化原始供应商事件、签名、配置或凭据。不启用完整 debug 日志。
- 按主题拆分，明确限制每个主题搜索次数、结果数量和摘要长度；“最多6条帖子”不是搜索次数限制。
- `--max-turns` 不是搜索次数上限：本次最终元数据 num_turns=1，但执行了16次搜索。需要精确硬上限时应由调用层计数并停止；提示词预算只能作为软约束。
- 总时限到达时应保留已白名单化的进度并明确标记未完成，终止该次远程进程组，避免遗留请求。本次诊断的远程控制程序已具备超时清理，所有测试正常结束。
- 本轮只是验证公开搜索；没有读到用户 Grok 网页里的私人定时任务，不将公开搜索冒称定时任务产物。

这些是本次验证后的调用约定，未写入远程全局配置。原始返回不进入正式研究证据；需另行核验原帖、时间和发行人/监管来源。
